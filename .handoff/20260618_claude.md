## What was done

- Migrated the local Neo4j graph (95,115 nodes, 21,022 relationships) into a
  Neo4j AuraDB Free instance ("Mgrid", id `2f88895b`) via
  `back/keeper_gate_bundle/bin/neo4j_golden_dump.sh` +
  `neo4j-admin database upload`. Verified counts match exactly on both sides.
- Fixed three real bugs found while running the golden dump script for the
  first time under load:
  - It dumped the wrong (empty, txn id 3) database because `NEO4J_CONF`
    wasn't set, so `neo4j-admin` fell back to `/etc/neo4j/neo4j.conf`
    instead of the actual running instance's conf
    (`back/services/mindgraph/mo-neo4j/conf`).
  - A previous failed dump sealed its output `chmod 444`, so
    `--overwrite-destination=true` silently couldn't write a fresh file —
    the script's success check only verified non-empty, not freshness.
    Added an age check (fails loudly if the dump file is >120s old) and an
    unlock-before-dump step.
  - `pm2 stop` only manages Neo4j's launcher process; the actual server
    runs as a separate child JVM that doesn't always exit when the
    launcher does, so the lock file could still be held when the dump
    started. Added a real `lsof`-based wait loop with a `pkill` fallback.
- Discovered this Aura instance's actual Bolt username AND database name
  are both the instance ID (`2f88895b`), **not** `neo4j` — the standard
  default. This cost several failed auth attempts before being found via
  `SHOW DATABASES` against the `system` db. Critical for any future Aura
  env var configuration on this project.
- Ran a live write test against Aura (one `Memory:GridKnowledge` node + one
  `MoStarMoment` node + the `[:SEALED_FROM]` relationship between them,
  using the exact Cypher from `mindgraph.learn()`/`stamp_moment()`) to
  verify the write path works end-to-end post-migration. Cleaned up after.
- Fixed a real cold-start crash: `back/services/mindgraph/__init__.py` had
  `from grid import glyphs` — `glyphs` was never used anywhere in the file
  and no `glyphs.py` module exists anywhere in the repo. This only worked
  locally because the local `mostar-grid` pm2 process has been running
  continuously since before this dead import was introduced (probably by
  the June 12 session); Render's cold start hit it immediately. Removed
  the import.
- Found and explained (but did not fix, not asked to) a real
  misconfiguration on the Render dashboard's `MoStar-Grid` service: its
  Environment tab was populated entirely with the **frontend's** env vars
  (`VITE_*`, `GRAPHCAST_*`, etc.) — none of the actual required
  `NEO4J_URI`/`USER`/`PASSWORD`/`DATABASE`/`PYTHONPATH` vars were present.
  Also flagged a real exposed secret: a base64 JSON blob containing a
  private EC key (looks like a Neo4j Aura API service-account credential)
  was pasted into an env var's **Key** field (unmasked) instead of a Value
  field — told the user to delete and rotate it.
